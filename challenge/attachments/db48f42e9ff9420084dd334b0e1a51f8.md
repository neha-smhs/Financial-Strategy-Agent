## Product decision

Build a trustworthy financial decision agent that determines whether a user can safely complete a requested expense while protecting essential commitments and the user minimum balance. The product must produce a valid recommendation when relevant information is distributed across structured records, messages, and images.

This PRD describes the implemented local architecture, decision contract, data and safety rules, evaluation results, and the next improvements required to increase benchmark accuracy.

# 1 Product overview

Buy or Wait answers questions such as Can I afford this laptop? using the user complete near term financial position. It evaluates current cash, recurring expenses, pending payments, confirmed income, flexible spending, payment preferences, available financing options, and evidence extracted from messages or images.

The product returns a recommendation for one request. It does not provide investment advice, predict asset prices, access live banking data, or authorize a real transaction.

## 1.1 Problem statement

Current balance alone is an unsafe affordability measure. A user may have enough cash today but face rent, utilities, debt payments, or essential spending before the next confirmed salary. Another user with the same balance may be able to proceed because their obligations, income timing, minimum balance, or accepted payment methods are different.

## 1.2 Goals

- Produce one valid output row for every request in requests.csv.

- Calculate the largest amount safe to pay on the request date before optional spending changes.

- Identify the earliest date a full single payment is safe within the 90 day horizon.

- Choose among full payment, partial payment, installments, waiting, or no recommendation.

- Respect user specific minimum balances, protected categories, spending permissions, and payment preferences.

- Use messages and images as evidence while preventing embedded instructions from overriding product rules.

- Provide deterministic validation, audit traces, and a measured evaluation workflow.

## 1.3 Non goals

- Live banking access, real transaction execution, or account authentication.

- Live exchange rates or market data.

- Security selection or asset price prediction for investment requests.

- A general purpose financial advisor outside the supplied request and forecast contract.

## 2.1 Representative use cases

- Pay the full request today when the complete forecast remains safe.

- Complete the request through an accepted installment offer.

- Pay a safe partial amount today and the remainder on the earliest safe date.

- Wait for confirmed income before making the full payment.

- Reject a request when no accepted plan completes by the deadline.

- Use a message or image to clarify an amended, delayed, cancelled, or settled event.

# 3 Product decision contract

The decision engine sends every candidate payment plan through the same 90 day safety check used to calculate the safe amount. A recommendation is safe only when every payment completes by the desired completion date, protected expenses remain covered, and the balance never falls below minimum_balance_to_keep.

| **Output field**               | **Product meaning**                                                | **Required behavior**                                 |
|--------------------------------|--------------------------------------------------------------------|-------------------------------------------------------|
| request_id                     | Original request identifier.                                       | Exactly one output row per input request.             |
| amount_safe_to_pay             | Maximum safe payment today before optional spending changes.       | 0 \<= value \<= requested amount.                     |
| affordability_status           | Overall affordability outcome.                                     | Use one of four allowed statuses.                     |
| recommended_payment_method     | Selected safe action.                                              | Use one of five allowed methods.                      |
| payment_plan                   | Chronological dates and amounts.                                   | YYYY-MM-DD:amount separated by \|, or none.           |
| earliest_date_for_full_payment | First date a full single payment is safe without optional changes. | Empty when no safe date occurs within the forecast.   |
| spending_changes_needed        | Allowed future flexible expense changes.                           | At most three stop or reduce_to actions.              |
| decision_explanation           | Short grounded rationale.                                          | Mention the action and relevant financial constraint. |

## 3.1 Status and method rules

| **Status**           | **Meaning**                                                                             | **Typical method**                             |
|----------------------|-----------------------------------------------------------------------------------------|------------------------------------------------|
| affordable_now       | Full amount is safe today and the user accepts full payment.                            | full_payment                                   |
| affordable_with_plan | Full amount can be completed using installments, partial payment, or permitted changes. | partial_payment, installments, or full_payment |
| affordable_later     | Full amount becomes safe later and the user accepts full payment.                       | wait                                           |
| not_affordable       | No eligible safe arrangement completes within the required constraints.                 | not_recommended                                |

# 4 Solution architecture

The implementation uses a hybrid pipeline. Evidence interpretation handles unstructured content. Deterministic financial logic remains the authority for money, dates, eligibility, ranking, and validation. This division gives the product language flexibility without allowing a model to invent or bypass a financial rule.

| **Stage**                | **Input**                                 | **Output**                             | **Implementation**                              |
|--------------------------|-------------------------------------------|----------------------------------------|-------------------------------------------------|
| Ingest                   | CSV files and local PNGs                  | Joined request context                 | main.py and common.py                           |
| Evidence interpretation  | Messages and linked images                | Structured facts with provenance       | evidence.py; Tesseract LSTM and bilingual rules |
| Financial reconstruction | Profiles, events, facts, FX rates         | Clean cash flows and recurring streams | forecast.py                                     |
| Forecast                 | Starting balance and future flows         | 90 day balance series and capacity     | forecast.py using Decimal                       |
| Plan generation          | Capacity, options, preferences            | Candidate plans and spending changes   | planner.py                                      |
| Verification             | Serialized recommendation and source data | Pass or failure with reason            | validate_output.py and independent replay       |
| Export and evaluation    | Validated rows and traces                 | output.csv, reports, hashes            | main.py and evaluate.py                         |

## 4.1 Why this architecture

- Financial constraints are exact and auditable, so arithmetic and rule enforcement are deterministic.

- Messages and images contain ambiguity, multilingual text, and document layouts, so they benefit from an evidence extraction layer.

- The planner compares multiple payment options without asking a model to reason about every numeric edge case.

- Independent replay catches invalid schedules, minimum balance breaches, unsupported changes, and schema errors before submission.

- The design works offline in the tested mode and supports an optional OpenAI compatible interpreter when credentials and a suitable vision model are available.

## 4.2 Implemented flow

The orchestrator loads a request and its user context, extracts relevant evidence, reconstructs cash flows, forecasts the next 90 days, computes unmodified capacity, enumerates eligible plans, applies the ranking criteria, validates the selected plan, and writes the output row plus an audit trace.

# 5 Data requirements and financial state

| **Source**                  | **Join key**                                    | **Role**                                             | **Important handling**                               |
|-----------------------------|-------------------------------------------------|------------------------------------------------------|------------------------------------------------------|
| requests.csv                | request_id, user_id                             | Request amount, dates, type, partial permission.     | Expected output fields are excluded from inference.  |
| financial_profiles.csv      | user_id                                         | Currency, balance, minimum, priorities, preferences. | Controls eligibility and spending changes.           |
| financial_events.csv        | user_id, event_id, linked_event_id              | Historical and future cash events.                   | Status and lifecycle determine cash treatment.       |
| request_payment_options.csv | request_id                                      | Seller or provider offers.                           | Installment plan must exactly match an offer.        |
| messages.csv                | user_id, request_id, related_event_id           | Amendments, confirmations, cancellations, delays.    | Untrusted evidence; explicit facts can update state. |
| images.csv and PNGs         | user_id, request_id, related_event_id, image_id | Amounts for selected events.                         | Blank amounts require image extraction.              |
| exchange_rates.csv          | Rate date and currency pair                     | Fixed dated conversions.                             | Use exact supplied direction and settlement date.    |

## 5.1 Event lifecycle rules

- Settled historical transactions are not replayed because the available balance is treated as a current cash snapshot.

- Pending debits are reserved once. Pending credits are excluded until settled.

- Failed and cancelled transactions are excluded unless a separate valid retry or obligation exists.

- Unrealized investment values are not spendable cash.

- Linked settlement, refund, authorization, and retry records are interpreted using cash status rather than link presence alone.

- Explicit cancellations, settlements, or amendments take priority over older conflicting records.

# 6 Forecasting and decision logic

## 6.1 90 day safety check

The forecast starts on request_date and includes the opening balance and every relevant cash flow through request_date plus 90 days. Recurring income and expenses are generated only when history supports a pattern. Essential and protected categories remain in the baseline forecast.

The safe amount is the largest today payment that leaves every projected balance at or above the user minimum, capped at the requested amount. The calculation is performed before optional spending changes, as required by the output contract.

## 6.2 Candidate plan generation

| **Candidate**    | **Eligibility and validation**                                                                                                                                                       |
|------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Full payment     | User accepts full_payment and the full request passes the forecast.                                                                                                                  |
| Partial payment  | Request allows it, user accepts it, safe capacity is positive but below request amount, and the remainder can be paid by the earliest safe date. Exactly two payments are generated. |
| Installments     | User accepts installments, offer is within max duration, total including fees reconciles, and every payment finishes by the deadline.                                                |
| Wait             | User accepts full_payment and the full request becomes safe later by the deadline.                                                                                                   |
| Spending changes | Only recurring non-protected expenses in categories the user permits may be stopped or reduced.                                                                                      |
| Not recommended  | Fallback when no eligible plan passes the safety check.                                                                                                                              |

## 6.3 Plan ranking

When multiple plans are safe, the implementation follows the challenge ranking order: complete by the deadline, require no spending changes, minimize total payment, start earlier, use fewer payments, then use the lowest payment option identifier.

# 7 Evidence interpretation

The tested submission uses Tesseract 5 LSTM OCR with two page segmentation passes and semantic total selection. Local message rules recognize common English and Indonesian payroll, payment, refund, transfer, and employment updates. The optional API path uses a constrained JSON schema and validates currencies, dates, amounts, and boolean fields.

## 7.1 Evidence principles

- Documents and messages are untrusted data. Embedded instructions cannot override product rules.

- Extracted facts retain source identifiers and quotations for auditability.

- Net salary is preferred over gross earnings when the document distinguishes them.

- Outstanding obligations distinguish the original amount from amounts already received.

- An unreadable amount is unresolved; it is never silently treated as zero.

- A newly confirmed essential obligation without an amount prevents safety certification rather than receiving a guessed amount.

## 8.1 Known performance limitation

The public sample safe amounts matched within one cent for 2 of 25 examples. The main gap is the exact organizer forecasting policy for variable expenses and recurrence. The implementation reports this limitation and does not present public sample results as hidden-test accuracy.

# 9 Assumptions and important considerations

| **Area**                 | **Assumption or consideration**                                                                    | **Risk if wrong**                                                    |
|--------------------------|----------------------------------------------------------------------------------------------------|----------------------------------------------------------------------|
| Same-day timing          | Debits are processed before credits when time of day is unavailable.                               | Can be more conservative than the hidden target.                     |
| Variable spending        | Recent-history median is used; upper-quartile sensitivity is retained.                             | Safe amount may differ from organizer forecast.                      |
| Recurrence               | At least three observations are required; grouping uses category and currency.                     | Distinct streams can be combined.                                    |
| Salary                   | Regular salary can continue monthly unless ended or amended; uncertain income is not extrapolated. | Future income may be under or over-estimated if evidence is unusual. |
| Images                   | OCR selects semantic totals and stores provenance.                                                 | Handwriting or complex tables may be misread.                        |
| Missing essential amount | No payment is certified when a new essential obligation has no amount.                             | Some cases are rejected conservatively.                              |
| Currency                 | Only supplied settlement-date FX rates are used.                                                   | Missing or reversed rates cause explicit failure.                    |
| Scope                    | Recommendations describe affordability under the reconstructed forecast, not financial advice.     | Forecasts should not be treated as guarantees.                       |

# 11 Operational requirements

- Run from the command line with Python 3.10+ and Tesseract 5 for local mode.

- Read all secrets from environment variables; never commit credentials.

- Keep the evidence cache content-addressed and preserve source hashes.

- Write evaluation/usage_report.md for every final full-dataset run.

- Retain per-request traces for debugging and review, without including sensitive credentials.

- Fail explicitly on unresolved future image amounts, missing FX rates, invalid input joins, or incomplete output rows.
